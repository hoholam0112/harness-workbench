# Concept Slides

개념을 남에게 **쉽게** 설명하는 단일 HTML 자료를 만든다. 페이지로 끊어 넘기는
zine 형식이고, **혼자 읽어서 이해되는 것이 합격 기준이다.**

핵심 원칙: **독자가 아직 모르는 것을, 이미 아는 것에 붙여준다.** 정의만 있으면
암기고, 비유만 있으면 오해다. 둘을 잇고 실물로 착지시켜야 이해다.

**이건 발표 슬라이드가 아니다.** 발표 슬라이드는 말이 주고 화면이 보조라서
비워도 됐다. 여기엔 말해줄 사람이 없다. 페이지에 없는 건 독자에게 영영 없다.

기본값: 한국어, 대상은 "이 분야를 모르는 동료 개발자", 기술 용어는 원어 병기(예:
파드(Pod)).

## 워크플로우

### 0. 인터뷰 — 질문 3개를 한 번에 묻는다

1. **독자** — 누구인가? 이미 아는 건 무엇인가?
2. **분량** — 개념 몇 개인가. (읽는 시간은 개념 수에서 나온다: Full 트랙 한 개념 ≈ 5~7분)
3. **단일 목표** — "독자가 이거 하나만 가져간다면 무엇인가?"

3번이 없으면 자료가 백과사전이 된다. 반드시 받아낸다.

### 1. 개념 분해 + 정의문 선행 검증 (사용자 승인 필요)

설명할 개념을 **의존 순서**로 정렬한다. 그리고 각 개념의 **한 줄 정의만 먼저 전부
써서** 사용자에게 보여주고 승인받는다. 슬라이드는 아직 만들지 않는다.

정의가 안 써지는 개념은 아직 이해가 덜 된 것이다. 여기서 걸러진다.

동시에 각 개념을 트랙에 배정한다:
- **Full (7장)** — 새롭고 헷갈리는 핵심 개념
- **Light (2장)** — 용어 하나, 도구 하나, 또는 독자가 주변 맥락을 이미 아는 경우

Light는 "짧은 트랙"이 아니라 "장 수가 적은 트랙"이다. 두 장뿐이라 각 장의 몫이
오히려 크다(두 장 모두 하한 200자).

### 2. 슬라이드 작성

`references/seven-beat.md`를 읽고 그 템플릿대로 쓴다. 장별 목적·하한·좋은 예/나쁜
예 대조가 거기 있다.

| 트랙 | 장 구성 |
|---|---|
| Full | ① 한 줄 정의 ② 왜 필요한가 ③ 비유(매핑표+깨지는 지점) ④ 어떻게 작동하는가 ⑤ 실제 모습 ⑥ 흔한 오해 ⑦ 정리+확인 질문 |
| Light | ① 한 줄 정의 + 필요성 ② 실제 모습 |

Light 트랙은 개별 정리 슬라이드를 만들지 않는다. 섹션 끝에 여러 개념을 묶어 한 장.

### 3. HTML 생성

`assets/deck.html`을 **복사해서** 슬라이드 내용만 채운다. 뼈대 CSS/JS를 재작성하지
않는다. 시각자료는 `assets/svg-kit.md`의 조각을 복붙해 라벨만 바꾼다.

**마크업 계약** — 검사기가 판정하려면 표시가 필요하다. 개념 슬라이드마다:

    <section class="slide" data-kind="how"
             data-concept="조정 루프" data-track="full">

- `data-kind` — `cover` `section` `define` `why` `analogy` `how` `real` `myth` `recap`
- `data-concept` — 개념 이름. **Full 트랙은 `recap`을 포함한 7장 전부에 필수.**
  `recap`에서 빠뜨리면 "개념 장인데 없다" 검사는 통과하지만(그 검사는 `recap`을
  안 본다), 대신 7단 완결성 검사에서 `개념 "X": recap 장이 없다`로 걸린다
- `data-track` — `full` 또는 `light`. 다른 값이면 문단 하한이 통째로 꺼지므로
  검사기가 모르는 값을 위반으로 잡는다

표지·섹션 구분 장에는 셋 다 붙이지 않는다. Light 묶음 정리 장(`recap`)은 여러
개념에 걸치므로 `data-concept`를 달지 않는다.

**설명 문단은 반드시 `.prose` 클래스가 붙은 요소로 쓴다.** 하한 계산은 태그를
가리지 않고 `.prose` 클래스만 본다 — `<p class="prose">`가 기본이고, `how` 장의
`<span class="prose why">`처럼 인라인 요소도 똑같이 세어진다. 불릿이나 표로는
통과할 수 없다 — 의도된 것이다.

### 4. 자기검사 → 열어보기

`deck.html`은 열릴 때 품질 게이트를 **자동으로 검사해서 콘솔에 출력한다.**
`window.__deckCheck()`를 호출하면 위반 목록이 배열로 나온다.

**위반이 0건이 될 때까지 고친다.** 브라우저 자동화 도구(Playwright 등)를 쓸 수 있으면
직접 실행해서 확인한다. 없으면 사용자에게 파일을 열고 콘솔을 확인해달라고 요청한다.
"아마 통과할 것"으로 넘기지 않는다.

통과 후 파일 경로와 조작키(`←/→`·`Space` 이동, `Home`/`End` 처음/끝, `o` 전체 보기,
`t` 테마, `f` 전체화면, `?` 도움말, `Esc` 닫기, `Cmd/Ctrl+P` PDF로 저장)를 알려준다.

## 품질 게이트

**자동으로 검사되는 것** — `__deckCheck()`가 잡는다:

| 게이트 | 한계 |
|---|---|
| 설명 문단 하한 (Full) | `define` 0 / `why` 250 / `analogy` 250 / `how` 300 / `real` 200 / `myth` 250 / `recap` 0 (글자) |
| 설명 문단 하한 (Light) | `define` 200 / `real` 200 / `recap` 0 |
| 하한 집계 대상 | `.prose` 클래스가 붙은 요소(태그 무관 — `<span class="prose why">`도 포함). 불릿·표 셀·코드·SVG 라벨·제목·`<details>` 내부는 0자로 친다 |
| 메커니즘 단계 | `how` 장에 `.steps > li` **3개 이상**. 2개면 인과 사슬이 아니라 대비다 |
| 코드 해설 | 모든 `<pre>`는 **같은 부모 안에** `.prose` 해설. `<pre>`가 `.slide` 직속이면 그 자체로 위반 |
| 확인 질문 | `recap` 장에 `<details class="quiz">` 1개 이상. 답은 접어둔다 |
| 7단 완결성 | `data-track="full"` 개념마다 7단이 전부 있어야 함(`recap` 포함, `data-concept`로 집계) |
| 슬라이드 표시 | 개념 장에 `data-concept` 필수(Full은 `recap` 포함, Light 묶음 `recap`은 예외), `data-track`은 `full`/`light`만 |
| 불릿 개수 | `recap` 3개, 그 외 6개 (`.pain li`, `.takeaways li` 기준) |
| 슬라이드 넘침 | 세로·가로 오버플로 0px. **글을 깎지 말고 레이아웃을 고친다** |
| 코드 가로 스크롤바 | 0. 잘린 코드는 못 읽는다. 2단 배치 40칸 / 전체 폭 70칸 |
| 이모지 | 2개. 픽토그램만, 장식 금지 |
| 제목 존재 | 모든 슬라이드에 `.headline` 또는 `.lede`가 적어도 하나 있어야 함 |
| 주제어 제목 | 그 제목에 "개요 / 이란? / 의 구조 / 의 특징" 류 어미 금지 |
| 비유 슬라이드 구조 | `.map`(매핑표)과 `.caveat`(깨지는 지점)이 반드시 있어야 함 |

하한을 못 채우면 물을 타지 말고 이해를 다시 한다. 대개 트랙 배정이 틀렸거나
기제를 아직 모르는 것이다 — `seven-beat.md`의 "하한을 못 채울 때"를 본다.
근거는 `references/principles.md`에 게이트별로 붙어 있다(하한·확인 질문은 독자
배경/retrieval practice, 코드 해설은 worked example + Spatial Contiguity, 제목은
Assertion-Evidence, 매핑표는 Feynman, 이모지 제한은 Coherence).

**사람이 판단해야 하는 것** — 검사기가 못 잡는다:

- **말로 보충해야 이해되는 문장이 남아 있지 않은가.** 이 스킬이 예전에 실패하던
  지점이다. 다 쓰고 나서 "이 부분은 설명하면서 덧붙이면 되지"라는 생각이 들면,
  그 덧붙일 말을 페이지에 쓴다.
- **제목이 진짜 완결된 문장인가.** 검사기는 뻔한 주제어 어미만 걸러낸다.
  ❌ "Pod의 구조" → ✅ "Pod은 같이 죽고 같이 사는 컨테이너 묶음이다"
- **SVG 라벨을 본문에서 그대로 되풀이하지 않는가.** 그림과 글이 토씨까지 같은 말을
  하면 둘 다 안 읽힌다. 글은 그림이 못 하는 말을 한다.
- **비유가 억지가 아닌가.** 억지 비유는 오개념을 심는다. 좋은 비유를 못 찾았으면
  **중단하고** 사용자에게 알린 뒤 개념 재분해를 제안한다.
- **정의가 순환하지 않는가.** X를 설명하는 데 X를 쓰지 않았는가.

### 시각자료는 규칙이 아니라 판단이다

> **이 페이지를 글로만 읽었을 때, 독자가 머릿속에 그림을 그려야 하는가?
> 그렇다면 그 그림을 내가 그려줘라.**

| 시각자료 필수 | 시각자료 불필요 |
|---|---|
| 구조 (무엇이 무엇 안에 있나) | 단일 용어 정의 |
| 흐름 (요청이 어디를 지나나) | 명령어 하나 |
| 관계 (누가 누구를 부르나) | 값·옵션 목록 |
| 시간순 변화 (전 → 후) | 한 줄 정의, 정리 슬라이드 |
| 비교 (A vs B) | — |

오른쪽 열에서는 `.prose` 문단이 혼자 그 장을 진다. 코드블록·표·큰 타이포는 산문을
대신하지 못한다 — 증거일 뿐이고 하한에도 세어지지 않는다. **그림이 없는 게 결함이
아니다. 필요한 곳에 없는 것이 결함이다.**

## 흔한 실패

| 증상 | 원인 | 처방 |
|---|---|---|
| 자료가 발표 슬라이드처럼 앙상함 | 페이지에 없는 건 독자에게 없다는 걸 잊음 | 각 문단에서 생략한 인과를 되살린다 |
| 메커니즘 장이 순서 나열로 끝남 | *왜*를 안 씀 | 단계마다 "왜 그 순서여야 하는가"를 쓴다 |
| 오해 장이 훈계가 됨 | 그럴듯한 오해를 못 찾음 | 자기가 처음 배울 때 틀렸던 걸 쓴다 |
| 확인 질문의 답이 뻔함 | 회상이 아니라 재확인 | 앞 장 문장을 그대로 묻지 말고 적용을 묻는다 |
| 비유가 "X는 Y다"에서 끝남 | 매핑을 안 함 | 매핑표를 붙인다. Y의 어느 부분이 X의 무엇인지 |
| 독자가 비유를 사실로 믿음 | 한계를 안 밝힘 | "이 비유가 깨지는 지점" 슬롯 채운다 |
| 정의가 순환함 | 설명 대상 단어를 설명에 재사용 | 상위 카테고리 + 결정적 차이로 다시 쓴다 |
| 개념 나열만 있고 왜가 없음 | 2장(왜 필요한가)을 건너뜀 | X 없을 때의 구체적 고통을 쓴다 |

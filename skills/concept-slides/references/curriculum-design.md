# 커리큘럼 설계

`curriculum.md`를 쓰는 법이다. 학습목표 쓰기, 챕터 쪼개기, 분량 검산이 여기 있다.

**`curriculum.md`의 형식은 이 문서가 정한다.** 다른 데는 없다. 짐작해서 쓰지 않는다.

챕터 안을 어떤 장으로 채우는지는 `references/chapter-anatomy.md`가 정한다.

## 1. `curriculum.md` 형식

```markdown
# <주제> 학습 과정

## 대상 독자
- 이미 아는 것: <구체적으로>
- 이번에 배울 것: <구체적으로>

## 과정 도달점
이 과정을 마치면 <한 문장으로, 할 수 있게 되는 것>

## 챕터

### 1. <제목>
상태: 완성
파일: ch01-<slug>.html
선수: 없음
학습목표
- g1: <…할 수 있다>
- g2: <…구분할 수 있다>

### 2. <제목>
상태: 대기
파일: ch02-<slug>.html
선수: 1장
학습목표
- g1: <…할 수 있다>
```

챕터 안의 네 줄은 **`상태` → `파일` → `선수` → `학습목표` 순서**로 쓴다. 값은 줄
이름으로 찾으므로 순서가 동작을 바꾸지는 않는다. 챕터마다 같은 자리에 같은 줄이
있어야 눈으로 훑기 쉽고, 고칠 때 diff가 한 줄로 남는다.

### 항목마다 왜 있는가

| 항목 | 왜 있는가 |
|---|---|
| `# <주제> 학습 과정` | 이 파일이 어느 과정의 것인지. 파일 하나에 과정 하나다 |
| `이미 아는 것` | 모든 설명의 출발점. 쉬운 설명 장이 여기에 걸린다 |
| `이번에 배울 것` | 범위의 경계선. 여기 없는 건 안 쓴다 |
| `## 과정 도달점` | 챕터 목표를 여기서 거꾸로 뽑는다. 도달점에 기여하지 않는 챕터는 뺀다 |
| `### N. <제목>` | 번호가 곧 학습 순서다. 순서는 의존 관계로 정한다(3절) |
| `상태:` | `대기` 또는 `완성`. 다음에 만들 챕터를 여기서 고른다 |
| `파일:` | 챕터 HTML 파일 이름. 챕터를 만들 때 이 이름을 그대로 쓴다 |
| `선수:` | 먼저 끝냈어야 하는 챕터. 챕터 열기 장의 "앞에서 배운 것"이 여기서 나온다. 없으면 `없음`, 여럿이면 `선수: 1장, 2장` |
| `학습목표` | 목표 목록. 챕터 HTML의 `.outcomes` 항목과 `data-goal` 값이 이걸 그대로 쓴다 |

### `상태:`가 호출 사이의 기억이다

이 스킬은 한 번 부를 때 챕터 하나만 만든다. 호출과 호출 사이에 남는 것은 이 파일
뿐이다. 어디까지 만들었는지를 아는 방법이 `상태:` 줄밖에 없다.

그래서 `상태:`를 틀리게 적으면 다음 호출이 엉뚱한 챕터를 만들거나, 이미 만든
챕터를 다시 만든다. **언제 `완성`으로 바꾸는지는 `SKILL.md`가 정한다.** 조건을 알아야
하면 거기를 본다.

### 목표 식별자는 챕터 안에서만 유효하다

`g1`, `g2`는 **그 챕터 안에서만** 통하는 이름이다. 챕터마다 `g1`부터 다시 센다.
2장에도 `g1`이 있고 3장에도 `g1`이 있다. 서로 다른 목표다.

챕터 HTML의 `data-goal` 값이 이 식별자를 그대로 쓴다. 챕터 하나가 파일 하나이므로
한 파일 안에서 겹치지 않으면 된다. 과정 전체에서 통하는 번호를 매기려 하지 않는다.

## 2. 학습목표 쓰는 법

**이 절이 과정의 품질을 정한다.** 목표가 부실하면 챕터도 부실해진다.

판정 기준은 하나다.

> **이 목표로 퀴즈를 만들 수 있는가. 못 만들면 목표가 아니다.**

목표와 퀴즈는 같은 문장의 앞뒤다. "…을 구분할 수 있다"라고 쓰면 "다음 둘 중
어느 쪽인가"라는 질문이 저절로 나온다. 반대로 퀴즈가 안 나오는 문장은, 무엇을
가르쳐야 하는지도 안 정해준다. 챕터를 쓰는 사람이 아무 방향도 못 받는다.

### 형식

    <대상>을 <어떻게> 할 수 있다

`<대상>`은 독자가 다룰 것이다. `<어떻게>`는 독자가 그것에 하는 일이다. 둘 다
있어야 퀴즈가 나온다. 대상만 있으면 범위이고, 동작만 있으면 구호다.

### 동사가 판정을 결정한다

| 확인할 수 있는 동사 | 무엇을 묻게 되는가 |
|---|---|
| 구분한다 | 두 경우를 주고 어느 쪽인지 묻는다 |
| 고른다 | 후보를 주고 근거와 함께 하나를 묻는다 |
| 찾아낸다 | 코드나 설정을 주고 문제 지점을 묻는다 |
| 예측한다 | 상황을 주고 결과를 묻는다 |
| 설명한다 | 결과를 주고 그렇게 되는 이유를 묻는다 |

| 확인할 수 없는 동사 | 왜 안 되는가 |
|---|---|
| 안다 | 안다고 했는지 아닌지를 밖에서 볼 방법이 없다 |
| 이해한다 | 같다. 이해의 증거를 정하지 않으면 아무것도 못 묻는다 |
| 익숙해진다 | 도달점이 아니라 상태다. 언제 도달했는지 정할 수 없다 |
| 살펴본다 | 훑는 행동이다. 훑고 나서 뭘 할 수 있는지를 안 말한다 |

**검사기가 `수 있다` 어미를 요구하는 이유가 이것이다.** 서식 규칙이 아니다.
확인할 수 없는 동사는 거의 다 `안다`·`이해한다`·`익숙해진다`·`살펴본다`로
끝난다. 어미를 보면 그 문장이 확인 가능한 목표인지 대체로 갈린다. 어미는 기계가
잡을 수 있는 절반이다.

나머지 절반은 사람이 본다. "훅을 이해할 수 있다"는 어미 검사를 통과하지만
목표가 아니다. **어미를 고쳐서 통과시키지 말고, 동사를 바꿔서 통과시킨다.**

### 나쁜 예

| 나쁜 목표 | 왜 목표가 아닌가 | 고친 것 |
|---|---|---|
| 리액트를 이해한다 | 확인할 방법이 없다. 무엇을 물어야 할지도 안 정해진다 | 어떤 상태 변경이 리렌더를 일으키고 어떤 게 안 일으키는지 구분할 수 있다 |
| 훅에 대해 배운다 | 배우는 건 수단이지 도달점이 아니다. 다 배운 뒤 무엇을 할 수 있는지를 안 말한다 | 의존성 배열을 잘못 써서 생기는 무한 루프를 코드만 보고 찾아낼 수 있다 |
| useState, useEffect, useMemo를 안다 | 목표 세 개를 하나로 뭉쳤다. 퀴즈가 세 개 나온다는 게 증거다 | 셋으로 쪼갠다. 목표마다 따로 확인해야 한다 |
| 타입스크립트 타입 시스템에 익숙해진다 | 익숙함은 상태다. 어디까지 가면 도달인지 정할 수 없다 | `any`와 `unknown` 중 무엇을 써야 하는지 근거를 들어 고를 수 있다 |
| 트랜잭션 격리 수준 네 가지를 살펴본다 | 훑는 활동이다. 게다가 네 개를 한 줄에 뭉쳤다 | 같은 조회를 두 번 했을 때 결과가 달라지는 격리 수준을 고를 수 있다 |
| SQL 성능을 개선할 수 있다 | 어미와 동사는 맞지만 너무 크다. 목표 하나는 15~25분이다 | 인덱스가 있는데도 안 쓰이는 쿼리를 실행 계획에서 찾아낼 수 있다 |

마지막 줄이 흔한 함정이다. **어미가 맞는다고 크기까지 맞는 건 아니다.** 목표
하나가 15~25분에 안 들어가면 쪼갠다.

### 좋은 예

| 목표 | 여기서 나오는 퀴즈 |
|---|---|
| 어떤 상태 변경이 리렌더를 일으키고 어떤 게 안 일으키는지 구분할 수 있다 | 상태 변경 코드 네 개를 주고 리렌더가 일어나는 것만 고르게 한다 |
| 의존성 배열을 잘못 써서 생기는 무한 루프를 코드만 보고 찾아낼 수 있다 | 돌아가는 컴포넌트와 무한 루프에 빠지는 컴포넌트를 나란히 주고 어느 줄이 원인인지 묻는다 |
| 스레드를 늘려서 빨라지는 파이썬 작업과 안 빨라지는 작업을 구분할 수 있다 | 작업 두 개를 주고 어느 쪽이 스레드로 빨라지는지, 왜인지 묻는다 |
| Dockerfile에서 한 줄을 고쳤을 때 어느 층부터 캐시가 깨지는지 예측할 수 있다 | Dockerfile을 주고 3번째 줄을 고쳤을 때 다시 빌드되는 층을 묻는다 |
| 충돌이 나는 병합과 안 나는 병합을 커밋 그래프만 보고 예측할 수 있다 | 그래프 두 개를 주고 어느 쪽이 충돌하는지, 어느 파일에서인지 묻는다 |
| 빌림 검사기가 거부하는 코드를 컴파일 전에 고를 수 있다 | 러스트 함수 세 개를 주고 컴파일이 안 되는 것과 그 이유를 묻는다 |
| 같은 질문에 답이 매번 달라지는 원인이 temperature인지 컨텍스트인지 구분할 수 있다 | 두 가지 증상 기록을 주고 각각 어느 원인인지 묻는다 |

공통점: 전부 **독자에게 무언가를 주고 판단하게 만들 수 있다.** 목표를 읽자마자
퀴즈의 모양이 보인다. 그게 잘 쓴 목표의 신호다.

## 3. 챕터로 나누는 법

순서대로 한다.

1. **도달점에서 목표를 다 뽑는다.** 과정 도달점에 도달하려면 무엇을 할 수 있어야
   하는지 나열한다. 아직 순서는 생각하지 않는다.
2. **의존 순서로 줄 세운다.** A를 모르면 B를 설명할 수 없으면 A가 앞이다. 판정
   방법: B의 설명을 소리 내어 해보고, 도중에 A의 용어를 쓰게 되면 A가 먼저다.
3. **목표를 챕터로 묶는다.** 한 챕터에 4~6개다.
4. **1장을 고른다.** 독자가 이미 아는 것에 가장 가까운 챕터를 1장으로 잡는다. 새
   지식은 이미 있는 것에 걸어야 붙는다. 걸 데가 없으면 1장부터 미끄러진다.
5. **선수를 적는다.** 챕터마다 `선수:` 줄을 채운다. 챕터 열기 장의 "앞에서 배운
   것"이 여기서 나온다.

### 챕터 하나의 크기

| 재는 것 | 값 |
|---|---|
| 읽는 시간 | 1~2시간 |
| 학습목표 | 4~6개 |
| 목표 하나 | 15~25분 |
| 슬라이드 | 60~70장 |

슬라이드 수는 목표가 아니라 결과다. 세어서 맞추지 않는다.

| 목표 개수 | 처방 |
|---|---|
| 7개 넘음 | 챕터를 쪼갠다. 1~2시간에 안 들어간다 |
| 4~6개 | 그대로 간다 |
| 2개 이하 | 앞이나 뒤 챕터와 합친다. 챕터 하나를 열 값이 안 된다 |

3개는 애매하다. 목표가 큰 편이면 두고, 작으면 옆 챕터와 합친다.

### 의존 순서를 잡을 때 자주 틀리는 것

- **어려운 것을 뒤로 미루는 게 의존 순서가 아니다.** 쉬워도 뒤에 필요한 게
  있으면 먼저다. 어려워도 앞에서 안 쓰이면 나중이다.
- **역사 순서로 정렬하지 않는다.** "예전에는 이랬고 그래서 이렇게 바뀌었다"는
  설명 방법이지 학습 순서가 아니다.
- **도구 사용법을 1장에 두지 않는다.** 명령어를 외우게 하고 개념을 뒤에 놓으면
  독자가 이유를 모른 채 따라 치기만 한다.

## 4. 분량 검산

챕터를 다 만든 뒤 검산한다. `window.__deckStats.minutes`가 추정 학습 시간이다.

    산문 글자수 ÷ 400 (분)
      + <pre> 줄수 × 6초
      + 그림(svg) 개수 × 30초
      + 퀴즈(.quiz) 개수 × 60초

| 구간 | 뜻 |
|---|---|
| 60~120분 | 목표 구간. 여기 들어오면 분할이 맞았다 |
| 50~140분 밖 | 콘솔에 경고가 뜬다 |

**목표 하나에 얼마를 쓸지는 이 공식을 거꾸로 돌려서 잡는다.** 목표 하나가
15~25분이면 산문 3000자 안팎이고, 코드와 그림과 퀴즈가 나머지를 채운다. 이 수치가
있어야 슬라이드를 몇 장으로 잡을지도 정해진다. `SKILL.md`의 목표별 산문 하한은
**통과선이고 목표치가 아니다** — 하한만 채우면 목표가 여섯 개여도 30분에 끝난다.

**이건 알림이고 위반이 아니다. 분량 때문에 챕터가 막히는 일은 없다.** 경고가 안
떴다고 분량이 맞은 것도 아니다 — 55분도, 135분도 경고 없이 통과한다. 그래서
경고가 아니라 60~120분을 기준으로 본다.

공식이 어림값이기 때문이다. 정독 속도는 주제에 따라 크게 다르다. 어려운 코드
10줄이 쉬운 산문 400자보다 오래 걸리는 일이 흔하다. 기계가 그걸 못 가른다.

### 벗어났을 때

> **커리큘럼으로 돌아가 목표를 다시 쪼갠다. 자료를 늘리거나 깎아서 숫자를
> 맞추지 않는다.**

| 증상 | 원인 | 처방 |
|---|---|---|
| 60분에 크게 못 미친다 | 목표를 너무 크게 잡아 각각을 얕게 썼다 | 목표를 쪼개서 개수를 늘린다. 쪼개면 설명할 것이 드러난다 |
| 120분을 크게 넘는다 | 챕터 하나에 목표를 너무 많이 넣었다 | 챕터를 둘로 나눈다. 뒤 챕터의 `선수:`에 앞 챕터를 적는다 |

물을 타서 늘리면 읽히지 않는 글자만 늘고, 깎아서 줄이면 독자가 못 따라간다. 둘
다 자료를 나쁘게 만든다. 숫자는 분할이 틀렸다는 신호이지 고칠 대상이 아니다.

## 5. 다 썼는지 확인

`curriculum.md`를 사용자에게 보이기 전에 훑는다.

- 목표마다 퀴즈를 하나 떠올릴 수 있는가. 안 떠오르는 목표는 다시 쓴다.
- 목표가 전부 `수 있다`로 끝나는가. `안다`·`이해한다`가 남아 있지 않은가.
- 한 줄에 목표 두 개가 뭉쳐 있지 않은가. 쉼표와 `및`이 신호다.
- 챕터마다 목표가 4~6개인가.
- 어느 챕터를 봐도, 그 챕터의 목표가 앞 챕터 내용만으로 설명되는가.
- 1장이 독자가 이미 아는 것에 붙어 있는가.
- 챕터마다 `상태`·`파일`·`선수`·`학습목표` 네 줄이 다 있는가.
- 목표 식별자가 챕터마다 `g1`부터 시작하는가.

## 부록 — 채운 예시

```markdown
# Git 내부 구조 학습 과정

## 대상 독자
- 이미 아는 것: `add` `commit` `push` `pull`을 매일 쓴다. 충돌이 나면 팀원에게
  물어보고 시키는 대로 한다.
- 이번에 배울 것: 커밋과 브랜치가 실제로 무엇인지, 그리고 병합과 리베이스가
  그것을 어떻게 바꾸는지.

## 과정 도달점
이 과정을 마치면 히스토리가 망가진 저장소를 보고 무슨 일이 있었는지 커밋
그래프로 설명하고, 되돌릴 방법을 골라 실행할 수 있다.

## 챕터

### 1. 커밋은 변경분이 아니라 그 시점의 스냅샷이다
상태: 완성
파일: ch01-commit-object.html
선수: 없음
학습목표
- g1: 커밋이 스냅샷이라는 근거를, 안 바뀐 파일이 두 커밋에 어떻게 저장되는지로
  설명할 수 있다
- g2: 커밋 메시지만 고쳤을 때 해시가 바뀌는지 안 바뀌는지 예측할 수 있다
- g3: `git cat-file` 출력에서 트리와 블롭을 구분할 수 있다
- g4: 파일을 지운 커밋을 만든 뒤에도 저장소 용량이 안 줄어드는 이유를 설명할 수
  있다

### 2. 브랜치는 커밋 하나를 가리키는 파일 한 줄이다
상태: 대기
파일: ch02-refs.html
선수: 1장
학습목표
- g1: 커밋을 새로 만드는 명령과 가리키는 곳만 옮기는 명령을 구분할 수 있다
- g2: `HEAD`가 분리된 상태에서 만든 커밋이 왜 안 보이게 되는지 설명할 수 있다
- g3: `git reset`의 세 가지 모드 중 작업 파일이 사라지는 것을 고를 수 있다
- g4: 브랜치를 지운 뒤에도 커밋이 남아 있는 기간을 예측할 수 있다
- g5: reflog에서 잃어버린 커밋을 찾아낼 수 있다

### 3. 병합과 리베이스는 같은 결과를 다른 그래프로 만든다
상태: 대기
파일: ch03-merge-rebase.html
선수: 1장, 2장
학습목표
- g1: 충돌이 나는 병합과 안 나는 병합을 커밋 그래프만 보고 예측할 수 있다
- g2: 같은 변경을 병합했을 때와 리베이스했을 때의 그래프를 각각 그릴 수 있다
- g3: 리베이스 뒤 강제 푸시가 팀원에게 무엇을 망가뜨리는지 설명할 수 있다
- g4: fast-forward로 끝나는 병합과 병합 커밋이 생기는 병합을 구분할 수 있다
```

세 챕터 다음도 같은 모양으로 이어진다. 눈여겨볼 것 셋이다. **목표가 전부
확인 가능한 동사로 끝난다.** **식별자가 챕터마다 `g1`부터 다시 시작한다.**
**`선수:`가 의존 순서를 그대로 적고 있다** — 3장은 그래프를 그려야 하므로 1장과
2장이 둘 다 필요하다.

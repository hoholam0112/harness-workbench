# concept-slides를 커리큘럼 기반 학습자료 스킬로 고치기 — 설계

작성일: 2026-07-29

## 왜 고치는가

이 스킬은 개발자가 **혼자 읽고 공부하는 자료**를 만든다. 그런데 지금 나오는
자료가 학습에 쓰이지 않는다. 사용자가 겪은 증상은 셋이다.

1. 뭘 알려주려는 자료인지 모르겠다.
2. 눈에 잘 안 들어온다.
3. 비유와 예시가 도움이 되는데, 형식 강제 때문에 오히려 방해가 된다.

원인은 하나다. **게이트가 "장(章)이 제 모양인가"를 재고 "독자가 배웠는가"는
안 본다.** 구체적으로 세 군데에서 새어나간다.

**원인 1 — 커리큘럼 층이 없다.** 학습 목표를 인터뷰 3번에서 **덱 전체에 딱
하나만** 받는다(`SKILL.md:27`). 섹션마다 "여기서 뭘 배우나 / 왜 배우나 / 지금
어디쯤인가"를 쓰라는 지시가 없고 검사 항목도 없다. `data-kind="section"`은
있지만 CSS만 있고 내용 규칙이 비어 있다 — 오히려 표시를 붙이지 말라고만 한다
(`SKILL.md:73`). 개념을 의존 순서로 정렬하긴 하는데 **그 순서를 독자에게는
보여주지 않는다.** 작성자만 안다.

**원인 2 — 고정 장 수가 가독성을 죽이고 내용을 부실하게 만든다.** Full 트랙
개념마다 7장이 전부 있어야 하고(`deck.html:673-682`), 장마다 산문 하한이
걸린다(`why` 250 / `analogy` 250 / `how` 300 / `real` 200 / `myth` 250,
`deck.html:596-599`). 개념 다섯이면 똑같은 일곱 장이 다섯 번 반복되고 장마다
문단이 강제로 찬다. 하한을 못 채우면 "이해를 다시 하라"고 적혀 있지만
(`SKILL.md:115`) 실제로는 물을 탄다. 균일하게 빽빽한 자료가 나온다.

**원인 3 — 도움 되는 것을 덜 시키고 억지스러운 것을 더 시킨다.** 비유는 Full
개념마다 **의무**다. 매핑표와 깨지는 지점이 둘 다 없으면 위반이다
(`deck.html:667-670`). 그래서 기계적인 비유가 양산된다. 반대로 실제 예시
(`real`)는 하한이 200자로 제일 낮다. 가장 잘 가르치는 장이 가장 가볍게
취급된다.

## 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 호출 단위 | 커리큘럼 설계 1회 + 챕터 작성 N회 | 한 번에 다 만들면 백과사전이 된다. 챕터 하나에 집중해야 분량이 채워진다 |
| 챕터 분량 | 읽는 데 1~2시간. 학습목표 4~6개, 슬라이드 60~70장 | 사용자 지정 |
| 진행 척추 | **학습목표.** 고정 장 수는 폐기 | 5단/7단 고정이 가독성을 떨어뜨리고 내용을 부실하게 만든 원인 |
| 설명 순서 | 쉬운 설명 → 엄밀한 설명 → 실제 예시 | 사용자 지정. **순서만 정하고 장 수는 안 정한다** |
| 비유 | 의무 아님. 적절할 때만 | 기계적 비유는 오개념을 심는다. 기본은 쉬운 설명 |
| 이해 검증 | 목표마다 퀴즈 하나 이상 | 목표를 "할 수 있다"로 쓰면 퀴즈가 따라 나온다 |
| 표시 형식 | 한 화면에 한 장 (지금 유지) | 사용자 지정. 넘침 검사와 PDF 출력이 살아남는다 |
| 산문 하한 | **목표 단위 하나로 통합.** 장별 하한 폐기 | 장별 하한이 물 타기를 유발했다 |
| 스킬 폴더 이름 | `concept-slides` 그대로 | 이름 변경 비용만 있고 얻는 게 없다. `description`만 새로 쓴다 |

## 새 구조 — 호출이 두 갈래로 갈린다

**첫 호출 = 커리큘럼 설계.** 주제·독자·도달점을 인터뷰하고 `curriculum.md`를
쓴다. 사용자 승인을 받고 **끝낸다. HTML은 만들지 않는다.** 지금 스킬이 인터뷰
직후 바로 슬라이드로 넘어가는 게 자료가 백과사전이 되는 원인이다.

**이후 호출 = 챕터 하나 완성.** "다음 챕터" 또는 "3장 만들어줘"로 지목하면
`curriculum.md`를 읽고 그 챕터 HTML 하나를 끝까지 만든다. 다 되면
`curriculum.md`의 상태를 `완성`으로 바꾼다.

`curriculum.md`가 이미 있으면 커리큘럼 설계를 건너뛴다. 없으면 챕터를
만들어달라는 요청이라도 커리큘럼부터 세운다.

세부 규칙 넷을 못 박는다.

- **출력 폴더**는 커리큘럼 설계 인터뷰에서 받는다. 이후 호출은 그 폴더의
  `curriculum.md`를 찾는다.
- **"다음 챕터"**는 `상태: 대기`인 첫 챕터를 뜻한다.
- **선수 챕터가 아직 `대기`면** 사용자에게 알리고, 그래도 진행할지 묻는다.
  앞 챕터의 내용을 모르면 "앞에서 배운 것"을 쓸 수 없다.
- **상태를 `완성`으로 바꾸는 시점**은 게이트 위반이 0건이 된 뒤다. 파일을
  만든 시점이 아니다.

### 출력물

```
<사용자가 정한 출력 폴더>/
  curriculum.md          ← 과정 설계 + 진도. 유일한 기준
  ch01-<slug>.html       ← 챕터 하나 = 파일 하나
  ch02-<slug>.html
```

`curriculum.md`가 호출 사이의 기억이다. md로 두는 이유는 둘이다. 호출 사이에
상태가 남아야 하고, 사람이 직접 읽고 고칠 수 있어야 한다.

### curriculum.md 형식

```markdown
# <주제> 학습 과정

## 대상 독자
- 이미 아는 것: <구체적으로>
- 이번에 배울 것: <구체적으로>

## 과정 도달점
이 과정을 마치면 <한 문장으로, 할 수 있게 되는 것>

## 챕터

### 1. <제목>
상태: 완성
파일: ch01-<slug>.html
선수: 없음
학습목표
- g1: <…할 수 있다>
- g2: <…구분할 수 있다>

### 2. <제목>
상태: 대기
파일: ch02-<slug>.html
선수: 1장
학습목표
- g1: <…할 수 있다>
```

목표 식별자 `g1`, `g2`는 **챕터 안에서만** 유효하다. 챕터마다 `g1`부터 다시
센다. HTML의 `data-goal`이 이 값을 그대로 쓴다.

### 학습목표 쓰는 법

**"할 수 있게 되는 것"으로 쓴다.** "리액트 렌더링에 대해 안다"는 목표가
아니다. 확인할 방법이 없다. "어떤 상태 변경이 리렌더를 일으키고 어떤 게 안
일으키는지 구분할 수 있다" — 이건 퀴즈로 검증된다.

목표와 퀴즈는 같은 문장의 앞뒤다. 목표를 이렇게 써야 챕터 끝 퀴즈가 저절로
나온다. 퀴즈를 못 만들겠는 목표는 목표가 아니다.

## 챕터 구조

```
챕터 표지        cover      — 번호·제목·추정 학습 시간
챕터 열기        opening    — 목표 선언 + 왜 배우나 + 전체 어디쯤
  ├ 목표 구분    goal       — "목표 1/5"
  │   쉬운 설명  intro
  │   엄밀한 설명 precise
  │   실제 예시  example
  │   함정·오해  pitfall    — 선택
  ├ 목표 구분    goal
  │   ...
챕터 닫기        closing    — 목표별 퀴즈 (여러 장이어도 된다)
```

목표당 설명 장은 10~12장쯤 된다. 표지 1 + 열기 1 + 목표 구분 5 + 설명 60 +
닫기 2 = 약 69장. 이 숫자는 목표가 아니라 결과다. 장 수는 안 정한다.

**3박자는 순서만 강제한다.** 목표 안에서 `intro` → `precise` → `example`이
이 순서로 최소 한 장씩 있어야 한다. 몇 장을 쓸지는 자유다. `intro`가 3장,
`precise`가 6장, `example`이 3장이어도 된다. 순서만 지키면 된다.

**비유는 의무가 아니다.** `intro`는 "쉬운 첫 설명"이지 "비유"가 아니다. 비유가
잘 맞으면 쓰고, 아니면 친숙한 사례·대비(A vs B)·축소 모형·문제 상황으로 쉽게
들어간다. 검사기는 비유가 있는지 **묻지 않는다.** 비유를 쓴 장에만 매핑표와
깨지는 지점을 요구한다.

### 마크업 계약

```html
<section class="slide" data-kind="precise" data-goal="g2">
```

**`data-kind`** — `cover` `opening` `goal` `intro` `precise` `example`
`pitfall` `closing`

폐기: `define` `why` `analogy` `how` `real` `myth` `recap` `section`

**`data-goal`** — `goal` `intro` `precise` `example` `pitfall` 장에 필수.
`cover` `opening` `closing`에는 붙이지 않는다.

**`data-analogy`** — 비유를 쓴 장에 붙인다(보통 `intro`). **이 표시가 붙은
장만** 매핑표·깨지는 지점 검사를 받는다.

폐기: `data-track`, `data-concept`

**설명 문단은 `.prose` 클래스로 쓴다.** 지금 규칙 그대로다. 하한 계산은
`.prose`만 세고, `<details>` 내부는 펼쳐져 있어도 세지 않는다. 불릿·표 셀·
코드·SVG 라벨·제목은 0자로 친다.

### 챕터 열기 장

```html
<section class="slide" data-kind="opening">
  <h2 class="headline">…</h2>
  <p class="prose">왜 이걸 배우는가 — 문단으로. 이 챕터를 건너뛰면 뒤에서
  무엇이 막히는지까지 쓴다.</p>
  <ul class="outcomes">
    <li data-goal="g1">…구분할 수 있다</li>
    <li data-goal="g2">…설명할 수 있다</li>
  </ul>
  <p class="progress-note">전체 6챕터 중 3번째 · 앞: … · 다음: …</p>
</section>
```

이 장이 사용자의 첫 번째 불만("뭘 알려주려는지 모르겠다")에 직접 답한다.
`.outcomes`가 목표 선언이고, 검사기가 이 목록을 기준으로 나머지 전부를
집계한다. 목록에 없는 `data-goal`은 미아로 잡히고, 목록에 있는데 장이 없는
목표도 잡힌다.

`.progress-note`에는 앞·다음 챕터 파일로 가는 상대 링크를 넣는다. 파일이
나란히 있으므로 상대 경로로 열린다.

### 챕터 닫기 장

```html
<section class="slide" data-kind="closing">
  <details class="quiz" data-goal="g1">
    <summary>…</summary>
    <p class="prose">답</p>
  </details>
</section>
```

목표가 다섯이면 퀴즈도 다섯이다. 한 장에 다 넣으면 넘치므로 `closing` 장을
여러 개 두어도 된다. 검사기는 위치를 안 따지고 `data-goal`만 본다 — 그래서
목표 구역 끝에 퀴즈를 두는 방식도 통과한다.

### 새로 넣는다

모양이 아니라 **학습이 성립하는지**를 본다.

| 게이트 | 조건 |
|---|---|
| 목표 선언 | `opening` 장에 `.outcomes li[data-goal]` 2개 이상 |
| 목표 어미 | 각 목표가 "할 수 있다 / 구분할 수 있다 / 설명할 수 있다"류로 끝남. "안다 / 이해한다 / 살펴본다"는 위반 |
| 열기 장 산문 | `opening` 장 `.prose` 400자 이상 |
| 목표↔장 연결 | `goal` `intro` `precise` `example` `pitfall` 장에 `data-goal` 필수 |
| 미아 목표값 | `data-goal` 값이 `.outcomes` 목록에 없음 |
| 빈 목표 | 선언은 했는데 설명 장이 하나도 없음 |
| 3박자 순서 | 목표마다 `intro` → `precise` → `example`이 **문서 순서대로** 최소 1장씩. 첫 `intro`가 첫 `precise`보다 앞, 첫 `precise`가 첫 `example`보다 앞이면 통과 — 그 뒤 되풀이는 허용한다 |
| 목표별 퀴즈 | 목표마다 `.quiz[data-goal]` 1개 이상 |
| 목표 산문 하한 | 목표 구역 `.prose` 합계 **1200자** |
| 비유 무결성 | `data-analogy` 장에 `.map`과 `.caveat` |
| 학습 시간 | 추정치가 50~140분 밖이면 **알림**(위반 아님) |

**목표 개수 게이트가 2개인 이유** — 권장은 4~6개다. 게이트를 4로 올리면
정당하게 짧은 챕터를 막는다. 게이트는 하한선이고, 4~6은 분량 지침이다. 실제
분량은 학습 시간 알림이 잡는다.

**학습 시간의 두 숫자** — 게이트 알림 구간은 50~140분이고 목표 구간은
60~120분이다. 알림 구간을 넓게 잡은 이유는 추정 공식이 어림값이기 때문이다.
알림이 안 떴다고 분량이 맞은 것은 아니다.

**열기 장에만 별도 산문 하한을 두는 이유** — 이 장은 목표에 속하지 않으므로
목표 단위 하한이 닿지 않는다. 하한이 없으면 불릿 목록만 남는다. "왜 배우나"가
사용자의 불만 중 하나였으므로 이 장은 비워둘 수 없다.

**목표 하한 1200자는 목표치가 아니라 안전망이다.** 목표당 10~12장이면 산문은
자연히 3000자를 넘는다. 1200자는 **너무 앙상한 목표만 걸러낸다.** 장 단위
압박을 없애는 것이 이 설계의 핵심이므로, 이 값을 올려서 다시 조이면 안 된다.

**학습 시간 추정 공식** — 어림값이다.

    산문 글자수 ÷ 400 (분) + <pre> 줄수 × 6초 + svg 개수 × 30초 + .quiz 개수 × 60초

커리큘럼 단계에서 잡은 분량이 실제로 맞았는지 검산하는 용도다. 위반이 아니라
알림인 이유는, 주제에 따라 정독 속도가 크게 다르기 때문이다.

### 그대로 둔다

넘침 0 / 코드 가로 스크롤 0 / 코드에 같은 부모 안 `.prose` 해설 /
`<pre>`가 `.slide` 직속이면 위반 / 제목(`.headline` 또는 `.lede`) 존재 /
주제어 제목 금지 / 이모지 2개 / 불릿 상한 6개(`.pain li`, `.takeaways li`)

## 뼈대(deck.html) 변경

**1. 검사기 교체.** 위 표대로 다시 쓴다. 슬라이드 순회 구조와 넘침 측정 방식
(`hidden`을 하나씩 풀어 실측)은 그대로 쓴다.

**2. 이어서 읽기.** 1~2시간 분량은 한 번에 못 읽는다. `localStorage`에 마지막
장 번호를 저장하고, 다시 열 때 1장이 아니면 "17장부터 이어 보기 / 처음부터"
배너를 띄운다. 주소 해시가 있으면 해시가 이긴다.

**3. 지금 어느 목표인지.** 현재 진행률 바(`#cur`/`#total`/`#fill`)는 챕터 전체
기준이라 목표 안에서의 위치가 안 보인다. HUD에 "목표 2/5 · 엄밀한 설명"을
`data-goal`과 `data-kind`에서 자동으로 찍는다. **슬라이드 안이 아니라 HUD에
넣는다** — 슬라이드 레이아웃을 건드리면 넘침 검사에 영향이 간다.

**4. 예시 슬라이드 교체.** 지금 들어 있는 파드 7단 예시를 새 구조 예시로
바꾼다(`cover` `opening` `goal` `intro` `precise` `example` `closing` 각 1장).
주제는 개발자 학습자료답게 고른다.

**5. `.outcomes`와 `.progress-note` CSS 추가.** `.map` `.caveat` `.steps`
`.quiz` `.pain` `.takeaways`는 그대로 쓴다.

## 안 하는 것

- **목차 HTML 생성.** `curriculum.md`와 각 챕터 열기 장이 이미 그 일을 한다.
- **따라치기 실습 지시.** 읽기 전용으로 정했다. 환경 설정·실행 결과·오류 대응을
  쓰지 않는다. 코드는 증거로 보여주고 해설로 이해시킨다.
- **스킬 폴더 이름 변경.** `concept-slides` 유지.
- **한 파일에 여러 챕터.** 챕터 하나 = 파일 하나.
- **장별 산문 상한.** 상한은 발표용 자료의 유물이고 이미 폐기됐다. 되살리지
  않는다.

## 검증

챕터 하나를 실제로 만들어서 확인한다.

1. `__deckCheck()` 위반 0건.
2. 추정 학습 시간이 60~120분 안.
3. 사람이 읽고 판단할 것 — 목표를 안 읽고 본문부터 봐도 "이 장이 뭘 가르치려는
   장인지" 알 수 있는가. 퀴즈를 목표만 보고 풀 수 있으면 자료가 없어도 되는
   퀴즈다. 본문을 읽어야 풀리는 퀴즈여야 한다.
